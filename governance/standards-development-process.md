# Standards Development Process

This document describes the TWG-FAS specification lifecycle and associated process controls.

## 1. Lifecycle States

TWG-FAS uses the following document maturity states:

1. Problem Statement
2. Proposal Draft
3. Working Draft
4. Public Review Draft
5. Candidate Standard
6. Published Standard

Optional supporting states:

- Snapshot Draft
- Technical Corrigendum
- Translation Draft

## 2. Stage Criteria

### 2.1 Problem Statement

Purpose:

- define the problem clearly
- explain why standardization is needed
- identify scope boundaries

Entry criteria:

- problem description
- motivation
- initial stakeholders

Exit criteria:

- agreement that scope is actionable

### 2.2 Proposal Draft

Purpose:

- present candidate technical approach
- capture trade-offs and alternatives

Entry criteria:

- accepted problem statement

Exit criteria:

- reviewer interest and initial technical viability

### 2.3 Working Draft

Purpose:

- produce structured technical specification text
- iterate rapidly with community input

Entry criteria:

- accepted proposal
- assigned editor

Exit criteria:

- stable baseline suitable for broader review

### 2.4 Public Review Draft

Purpose:

- gather broad external and cross-domain feedback
- validate clarity and interoperability assumptions

Entry criteria:

- working draft with known open issues classified

Exit criteria:

- review comments resolved or dispositioned
- unresolved high-severity issues tracked with explicit rationale

### 2.5 Candidate Standard

Purpose:

- finalize technical content pending implementation/conformance evidence

Entry criteria:

- public review closure report
- change log summary
- no unresolved blocker issues

Exit criteria:

- at least one implementation evidence package
- conformance criteria defined

### 2.6 Published Standard

Purpose:

- declare stable, versioned specification for general use

Entry criteria:

- candidate standard approval
- publication package complete

Exit criteria:

- standard published with version, date, and change history

## 3. Core Process Phases

The end-to-end process should include:

1. Draft development
2. Review and comment collection
3. Change request resolution
4. Consensus check and, if required, voting
5. Approval and publication

## 4. Change Request Handling

All substantive comments should be tracked as change requests in repository issues or equivalent tracked artifacts.

Each change request should include:

- affected section
- rationale
- suggested text or expected behavior
- severity/priority
- disposition (accepted, rejected, deferred)

## 5. Review Windows

Recommended default windows:

- targeted technical review: 2-4 weeks
- broad public review: 4-8 weeks

Shorter windows may be used for narrowly scoped corrections with clear rationale.

## 6. Publication Artifacts

A publication package should include:

- final specification source
- rendered deliverable (for example PDF)
- change log from previous version
- known limitations and open follow-up list
- conformance statement template (if applicable)

## 7. Maintenance After Publication

Post-publication maintenance may include:

- errata
- corrigenda
- clarifications
- compatibility notes

Normative changes after publication should trigger a new version cycle.
